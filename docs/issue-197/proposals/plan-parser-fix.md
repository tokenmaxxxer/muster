## Request

이슈 #197: `gates/flows.py:81` `_plan_from_body`가 실물 이슈 본문에서 틀린
데이터를 낸다 — 이슈-189 execution-observation 판정(finding 1)이 확정한 결함.
원인 둘: (1) 코드펜스 무인식 — 펜스 안 문서 예시의 `## 실행 계획` 줄이 실제
계획보다 먼저 매치, (2) 헤더 정확 일치 — 괄호 설명이 붙은 실제 헤더가 매치
안 됨. 스펙(`run.md`의 실행 계획 문법) 자체가 펜스·헤더 변형에 침묵한 것이
근본 원인이므로 코드와 문법 정의를 함께 고친다. 회귀 픽스처는 이슈-189 실물
본문을 그대로 써야 한다 — 합성 픽스처만으로는 finding 2(같은 판정)가 지적한
과대주장이 재발한다.

## Constraints

- `_plan_from_body`의 반환 계약은 그대로: `None`=블록 없음, 리스트(빈 리스트
  가능)=블록 있음. `flows_payload`(`flows.py:222`, `:226`)의 두 소비 지점이
  이 계약에 의존한다 — 안 바꾼다.
- `_PLAN_STEP_RE`(`flows.py:69`)는 안 건드린다 — 이슈-189 판정이 이미 결함
  아님으로 확정.
- `docs/specs/flows-schema.md`의 `plan` 필드 형태는 안 바뀐다(이슈 본문 명시
  범위 밖) — 파싱 소스만 고친다.
- 기존 `test_spawn.py::FlowsPayload`의 플랜 테스트 3개는 그대로 통과해야
  한다(펜스 없음·정확 일치 헤더만 쓰는 케이스라 새 로직에서도 동일 결과 —
  hunt pass로 수기 검증 완료, 아래 Rationale).
- 새 의존성 추가 금지 — 이 레포에 마크다운 파서 라이브러리 의존성이 현재
  없다.

## Rationale

**채택: 펜스 토글 플래그 + 공백-경계 전방일치 헤더 + 첫-매치-우선(변경 없음).**
셋 다 survey/scout-brief가 근거를 남겼다:

1. 펜스 토글은 새로 발명하지 않는다 — `gates/gates.py:387-392`
   (`record_no_tool_residue_in`)에 이미 검증된 동일 패턴(``` 로 시작하는 줄마다
   `in_fence` 반전, `in_fence` 동안 스킵)이 있다. **거부한 대안(rejected
   alternative)**: 전용 마크다운 파서 라이브러리 도입 — CommonMark 완전
   호환 파서는 이 레포가 다루는 좁은 구조(ATX 헤딩 + 체크박스 리스트)에
   비해 과잉이고, 새 의존성이 필요해 no-footgun 방침과 충돌한다. 기존
   레포 관용구를 재사용하는 쪽이 **rather than** 새 라이브러리를 끌어오는
   쪽보다 검증 비용이 낮다.
2. 헤더 매칭은 `stripped == "## 실행 계획" or stripped.startswith("## 실행 계획 ")`
   (뒤에 리터럴 공백을 요구) — 이슈 #197 본문의 "방향" 절 후보(헤더
   전방일치)를 채택한다. **거부한 대안(rejected alternative)**: 괄호 접미사만
   허용하는 좁은 정규식 `^## 실행 계획(?:\s*\(.*\))?\s*$`. 이슈-189 실물
   헤더 한 건만 보면 이 패턴도 맞지만, 이 좁은 정규식을 채택하는 대신
   (**instead of** the narrow paren-only regex) 일반 공백-경계 전방일치를
   택한 이유는 이슈 #197 본문이 스스로 제시한 후보가 이미 일반 전방일치이고,
   괄호로 한정할 근거(이 레포의 다른 이슈들도 항상 괄호를 쓴다는 증거)가
   survey에서 나오지 않았기 때문이다 — 한 예시에 과적합할 위험이 더 크다고
   판단해 기각(rejected)했다. 공백 경계 요구만으로 `## 실행 계획서` 같은
   동명 오매치는 막힌다(매치 안 됨: "계획" 다음 글자가 공백이 아니라 "서").
3. 복수 비-펜스 매치 처리: **거부한 대안(rejected alternative)**:
   `closure_sweep`에 새 위반 종류(예: "중복 계획 헤더")를 추가해 감지·보고.
   이 대안을 기각한(rejected) 이유 — (a) 이슈 #197 본문 자체가 스키마·게이트
   변경을 범위 밖으로 명시, (b) 이슈-189 본문의 54개 이슈 측정(멀티스텝조차
   5/54)에서 실제 이 레포 이슈 본문 중 복수 계획 헤더가 관측된 사례가 0건,
   (c) `flows.py` 모듈 자체 계약("아무것도 안 고치고, 안 posting 한다")과
   순수 함수 유지 원칙에 새 위반 종류 추가가 부담 대비 이득이 낮다. 새 게이트를
   추가하는 대신(**instead of** adding a new gate), 기존 `break`(첫 번째
   비-펜스 매치에서 멈춤) 동작을 그대로 유지하고, `run.md` 문법 절에 "본문에
   펜스 밖 계획 헤더는 정확히 하나여야 하며 여럿이면 첫 번째만 쓰이고 이는
   저작 오류로 간주한다"를 명문화한다 — 코드 변경 없이 계약을 명시하는 쪽이
   이번 요구(3번, 문법 정의 갱신)에 정확히 대응한다.

**hunt pass(adversarial, general-purpose 에이전트, 이 세션에서 포그라운드로
실행·완료)가 위 설계를 실제 파일과 이 레포 이슈 본문 64건 전체를 대조해
검증했다.** 확인된 잔여 리스크 2건, 둘 다 의도적으로 이번 범위 밖으로
남긴다:

- **펜스 미종료(홀수 개수) 시 나머지 문서 전체가 "펜스 안"으로 남아 실제
  헤더를 놓칠 수 있다.** hunt pass가 `gh issue list`로 이 레포의 살아있는
  이슈 본문 64건 전부를 스캔해 펜스 개수가 모두 짝수임을 확인 — 현재
  트리거되지 않는다. 실패 모드도 안전한 방향이다: 틀린 계획을 보고하는 대신
  `None`(계획 없음)을 반환한다 — 이번 버그의 실제 피해(틀린 계획을 보여줌)와
  반대 방향이라 우선순위가 낮다. 실측 사례가 나오면 별도 이슈로 다룬다
  (이슈-189 판정이 `--limit 1000`·`_PLAN_STEP_RE` 간격을 "실측 없음 → 결함
  아님"으로 처리한 것과 같은 기준).
- **펜스로 감싸지 않은 채 계획 형식을 인용/설명하는 줄이 있으면 여전히
  오매치될 수 있다** (코드펜스 무인식은 고쳤지만, "펜스를 깜빡 안 씌운 경우"는
  별개 저작 실수). `run.md` 문법 절에 "형식을 설명·인용할 때는 반드시
  코드펜스 안에 넣는다"를 명시적으로 추가해 이 리스크를 문서 계약으로
  옮긴다 — 요구 3(문법 정의 갱신)이 정확히 이 지점을 메운다.
- 틸드(`~~~`) 펜스, 4자 이상 백틱 펜스 길이 매칭: 같은 64건 스캔에서 전부
  3자 백틱만 씀 확인, 미지원 상태 유지(실측 없음).

**hunt pass가 추가로 발견한, 회귀 픽스처 설계에 반영해야 할 사실**: 이슈-189
실물 계획 블록의 스텝 줄은 `- [x] step 1  product-discovery — 요구사항·수용기준
확정, 위 갭에 대한 접근 결정`처럼 역할 토큰 뒤에 설명 접미사(em dash)가
붙어 있다. `_PLAN_STEP_RE`(안 건드림)의 `(.+)$`가 이 접미사까지 role
문자열에 그대로 캡처한다 — 이는 승인된 문법(§1.1, `<role>[ ‖ <role2>...]`,
접미사 미정의)에 대한 **이슈-189 본문 자체의 비순응**이며, `_PLAN_STEP_RE`
변경은 이번 범위 밖이므로 손대지 않는다. 회귀 테스트는 이 실제 캡처 결과
(접미사 포함 role 문자열)를 있는 그대로 단언한다 — 기대값을 깨끗하게
다듬어 테스트를 통과시키는 것은 실물 검증이 아니라 조작이 된다.

## What will be done

1. **`gates/flows.py`**: `_plan_from_body`를 헤더 탐색 루프·스텝 수집 루프
   둘 다에 `gates/gates.py`와 동일한 `in_fence` 토글을 적용하도록 고친다.
   헤더 비교를 `line.strip() == "## 실행 계획"`에서
   `stripped == "## 실행 계획" or stripped.startswith("## 실행 계획 ")`로
   바꾼다. 반환 계약(`None`/리스트)은 그대로.
2. **`on-the-record/commands/run.md`** `## 실행 계획 (Execution Plan)` →
   `### 문법` 절에 추가: (a) 형식 견본·설명은 반드시 코드펜스 안에 넣는다 —
   펜스 밖에 있으면 실제 계획 블록으로 오인식된다, (b) 헤더는 `## 실행 계획`로
   시작하고 뒤에 공백+부가 설명이 붙을 수 있다(예: 괄호 설명), (c) 본문에는
   펜스 밖 계획 헤더가 정확히 하나여야 하며 여럿이면 첫 번째만 파싱되고
   이는 저작 오류로 간주한다.
3. **`test_spawn.py`**: `FlowsPayload`에 회귀 테스트 추가 — 이슈-189의 실제
   본문(`gh issue view 189 --json body`로 받은 전문, 리터럴 문자열로 픽스처에
   포함)을 그대로 써서 `plan_by_issue[189]`(또는 동등한 `flows[]` 항목)가
   펜스 안 4-스텝이 아니라 실제 3-스텝(역할 문자열은 위 Rationale의 접미사
   포함 형태 그대로)을 낸다고 단언한다. 보조로 합성 케이스 2개 추가(주 증거를
   대체하지 않음, 명시적으로 그렇게 코멘트) — 펜스만 있고 실제 헤더가 없는
   본문 → `None`, 비-펜스 헤더가 두 개인 본문 → 첫 번째 채택.
