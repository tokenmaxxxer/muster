### Observed
`role_settings()` (spawn.py:477-499) runs, for any role with `sandbox.enabled`:
```python
for host in PACKAGE_REGISTRY_HOSTS:
    if host not in domains:
        domains.append(host)
for host in WEB_ACCESS_DOMAINS:   # WEB_ACCESS_DOMAINS = ["*"]
    if host not in domains:
        domains.append(host)
```
`WEB_ACCESS_DOMAINS = ["*"]` (spawn.py line ~141) is merged unconditionally, right after
PACKAGE_REGISTRY_HOSTS, for every sandboxed role, with no scoping to WebSearch/WebFetch
tools at the network (allowedDomains) layer — the code comment at line ~527-529 confirms
this "*" only additionally opens a second, separate TOOL-PERMISSION layer for
WebSearch/WebFetch, but the NETWORK layer wildcard is already in `allowedDomains` for
every sandboxed role regardless. Separately, `roles/implementation.json` already
hand-declares `"github.com"` and `"*.github.com"` in its own
`sandbox.network.allowedDomains`, so for the very role this proposal is meant to fix,
github.com access is already granted twice over before phase 2 is even written.

### Expected
If PACKAGE_REGISTRY_HOSTS is the mechanism meant to gate cargo's github.com dependency
fetches (per the phase-2 proposal), then adding "github.com" to it should be the thing
that newly grants that access. Instead, the pre-existing "*" merge (issue #58) already
puts a literal wildcard in the same `allowedDomains` array for every sandboxed role, so
the NETWORK-layer restriction PACKAGE_REGISTRY_HOSTS nominally enforces is already void
before the phase-2 change is applied — the survey's premise that github.com is currently
unreachable at the sandbox network layer does not hold for any role with sandbox.enabled,
and the proposed edit is a no-op at that layer.
